# K.S Management (formerly KeyOfSuccess, TaskFlow)

Asana-like task manager for a Marketing department of about 40 people.
React + Vite (`client/`), Node/Express + SQLite via `node:sqlite` (`server/`). Run with `npm run dev` from the repo root, or in the background with pm2: `pm2 start ecosystem.config.cjs` (stop it with `pm2 stop keyofsuccess-dev` before a schema change; README › Cài đặt › Chạy).
README.md documents setup, env vars, permissions and the API.

Server layout (split 2026-10-06): `server/src/index.js` only builds the app; each feature's endpoints are an `express.Router` in `server/src/routes/<feature>.js` (mounted under `/api`), and rules or helpers used by more than one route live in `server/src/lib/` (access rules in `lib/access.js`). A new endpoint goes in its feature's route file, never back into `index.js`.

Client layout (split 2026-10-06): screens live in `client/src/features/<feature>/`, components shared by several screens in `client/src/components/` (one file per concern: `Avatar`, `TaskParts`, `Mentions`, `Controls`, `Preferences`, `hooks`, `Dialog`, `CurrentUser`), styles in `client/src/styles/` imported in order by `styles/index.css` (tokens first, `responsive.css` last; new rules go in the matching file, before `responsive.css`). Import straight from the file that defines a thing; there is no barrel file.

Production (2026-10-06): `npm run build` then `npm start` with `NODE_ENV=production` in `server/.env`; one process serves the API and `client/dist`, HTTPS comes from a reverse proxy (`deploy/Caddyfile`, `deploy/keyofsuccess.service`). `config.js` refuses to start without a real `JWT_SECRET` / `GOOGLE_CLIENT_ID` or with `DEV_LOGIN`. Daily backups of the database and uploads (`lib/backup.js`, `BACKUP_DIR`, `npm run backup`); any new folder of user data under `server/data/` must be added to them. Versions are git tags on `main`; `deploy/update.sh [tag]` deploys one (backup first, automatic rollback if the app does not come up), `deploy/rollback.sh [--list | tag]` goes back (code only when the schema matches, else restores the pre-deploy backup); history in `server/data/deploys.log`. Migrations only run forward, so a schema change makes rolling back cost the data entered since. `DEPLOY.md` is the step-by-step guide (keep it in step with the scripts); README › Deploy has the technical details.

Tests: `npm test` (node:test, `server/test/*.test.js`, about 5 seconds). Each file starts its own API on a free port with a temporary database, so it is safe while the dev server runs. Run it after every server change; a new rule or endpoint gets tests in the matching file (helpers in `server/test/helpers.js`). Do not write ad-hoc curl scripts for API checks.

Schema changes: `npm run dev` runs the server with `node --watch`, so saving `server/src/db.js` immediately runs new migrations on the real `server/data/app.db`. Before editing the schema, stop the dev server and back up the database (`VACUUM INTO 'data/app.backup-<name>.db'`), then test migrations on a copy.

## Languages (decided 2026-10-06, schema v19)

The interface is in Vietnamese or English, per account (`users.language`, `PATCH /api/me`, VI | EN switch in the sidebar and on the sign-in / waiting screens; default Vietnamese). Every user-facing text in the client goes through `tr('Vietnamese text', { params })` from `client/src/i18n.js`, with its English in `client/src/i18n.en.js` (the Vietnamese is the key; `{name}` placeholders). Never translate user content (project, task, status, requirement names). Label tables and other module-level text must be getters or functions so they read the current language. The server keeps answering in Vietnamese; `trMessage()` translates its errors, so a new server message needs an English entry too. `server/test/i18n.test.js` fails on a missing English text or a Vietnamese text outside `tr()`. Dates use `locale()`.

## UI design

App name (decided 2026-10-10): "K.S Management", K and S being KingSport's initials (it was "KeyOfSuccess" from 2026-10-06; earlier "TaskFlow"). On screen it is always `<Brand />` (`client/src/components/Brand.jsx`, one `aria-label`): every letter the same size (the user chose it the same day over a first try with K and S 4× bigger), K and S in `--brand` (large text only, so never below `--brand-size` 20px); the tab title is in `client/index.html`. Server, deploy and repo names keep "keyofsuccess" (`/opt/keyofsuccess`, the systemd service and user, pm2 `keyofsuccess-dev`): renaming them would break deploys; `--brand-size` sets the size (20px sidebar and top bar, 32px sign-in card, 26px there on phones). In the sidebar the deployed version sits under it (`AppVersion`, the tag from `GET /api/health`, "bản dev" otherwise). Internal ids keep the old name (`taskflow_theme` in localStorage, the `taskflow-theme` event): renaming them would reset saved choices.

Before any UI work (components, CSS, layout, colors, typography), read `.claude/DESIGN.md` and follow its tokens and do/don't rules.

Exception, chosen by the user: colors follow the KingSport brand (red-white), not DESIGN.md's Action Blue. The tokens live in `client/src/styles/tokens.css`:
- `--brand` #D85A30 (only 3.87:1 on white): large fills, chart marks, login background. Never small text.
- `--primary` #C24E26: buttons and other filled controls with white text (4.76:1).
- `--primary-text` #993C1D: links and red text on white.
- Overdue/destructive is crimson `--danger` #B42318 and always pairs with a ⚠ icon, because it sits close to the brand red.
- Light and dark themes: `:root` holds light tokens, `:root[data-theme='dark']` overrides them (index.html sets `data-theme` before first paint from localStorage `taskflow_theme`, else the OS preference). Never hard-code a color outside those token blocks, except the sidebar's own `--sb-*` tokens (dark #1E2027 panel from `component_styles/side_bar`, same in both themes, brand red only as accent). Re-check contrast (and chart pairs with the dataviz validator) for both themes when adding colors.

## Product rules (decided with the user, 2026-10-05)

- Root (decided 2026-10-06, schema v23): accounts in `ROOT_EMAILS` (`users.role = 'root'`) are not part of the company. They only configure the system on the "Cấu hình hệ thống" screen (`SystemConfigPage.jsx`, shown instead of the Workspace): roles (the Director role included), status and teams of people. `ROOT_ROUTES` in `routes/auth.js` lets them reach only `/me`, `/admin/users`, `GET /teams`, roles / permissions and avatars, plus (v31) the feedback routes, their own notification counts and event stream and feedback files; everything else is 403, and they read nobody's personal details. Root has no teams and is left out of every list of people (`u.role != 'root'` in the user list, team candidates, `/people`, the dashboard workload, adding project members); nobody changes a root account in the app (404), and an email taken out of `ROOT_EMAILS` loses access at the next request. Root is not a role anyone can give. Root also edits the permissions (below).
- Permissions (decided 2026-10-06, schema v24): what each role may do is data, set by root ("Quyền theo vai trò" on the System configuration screen): `roles` (key, name, `level`) and `role_permissions` (role, permission, scope `none` / `team` / `all`). The catalog and the defaults live in `server/src/lib/permissions.js`; the defaults are the rules described in this file, which therefore describe default behaviour. Never check `user.role` for a right: use `can()` / `scopeOf()` / `coversTeams()` (server `lib/permissions.js`, client `utils.js` reading `user.permissions` from `/api/me`) or the `requirePermission(key)` guard; a new right gets a new permission with its defaults (seeded at startup). Role levels replace the hard-coded Director rule: nobody changes the account of, gives, or reads the profile of a role above their own (`outranks()`, root above all). Roles are editable (decided 2026-10-07, schema v27): root adds a role as a copy of another (permissions and team rule) at a level it picks, renames any role, deletes an added role nobody holds (pending and locked accounts count); the four built-in roles (`roles.builtin`) keep their level and are never deleted, since sign-up and Leader invitations give `member` and `MANAGER_EMAILS` / `DIRECTOR_EMAILS` give `manager` / `director`. Each role carries its team rule, `min_teams` 0 / 1 and `max_teams` 1 / NULL (no limit): never test `role === 'member'` or `'leader'` for team counts, use `teamLimitsError()` / `singleTeam()` (server) or `roleIn(roles, key)` (client); a rule cannot change while a holder breaks it. Without users.manage, team member management reaches people of a lower level only. `users.role` has no CHECK since v27. Role names come from the server (`role_name` in `USER_SELECT`, `roleLabel(user)` in the client), never from a hard-coded list.
- Managers run their own teams only (decided 2026-10-06, schema v26): every team-scoped Manager permission defaults to 'team' (projects.view, projects.change_teams, requirements.manage, people.watch, people.profiles, users.manage, teams.members, teams.manage, notify.task_completed); only the Director sees the whole department. users.manage 'team' covers the people of one's teams and those with no team (never a higher role) and places them only in one's teams (`mergeOwnTeams()` keeps their other teams); teams.manage 'team' renames one's teams, creating / deleting needs 'all' (decided 2026-10-08: someone creating a team without users.manage 'all' joins it, if their role's team rule allows, else they could neither see it on the Administration screen nor place anyone in it); projects.change_teams 'team' picks among one's teams, at least one. The rules below that say "Managers see everything" / "every project" describe a Manager given 'all' by root. Test files written before v26 run with the Manager at 'all' (`startServer()` in `server/test/helpers.js`); `startServer({ managerScope: 'team' })` tests the default.
- Director (decided 2026-10-06, schema v22): above the Managers, full rights on the whole system. Has every Manager right (`isManager()` in `server/src/lib/roles.js` and `client/src/utils.js` is true for both; use it, not `role === 'manager'`, for Manager-level rights), plus `manage` access and task admin on every project, assigning anyone of the project's teams. Only a Director or root gives / removes the Director role or changes a Director's account (role, status, teams); a Director's profile is for Directors only. Directors get no `task_completed` notifications. `DIRECTOR_EMAILS` bootstraps them (Trieu is Director); `MANAGER_EMAILS` never demotes a Director. The lists give their role once (decided 2026-10-07, schema v29: `users.env_role` = the role the lists last gave; sign-in applies it only when the lists say something new), so a role change or a lock made in the app survives the next sign-in; `envRoleOf()` in `config.js`. A Director belongs to any number of teams, like a Manager.
- Roles: Manager runs the whole department and is also admin; Leader runs one or more teams. Teams live in `user_teams` (v9; `users.team_id` is unused legacy): a Member belongs to exactly one team, a Leader to at least one and leads all of them, a Manager to any number. Users carry `teams`, `team_ids` and `team_name` (names joined).
- Visibility: Members see only projects they belong to and must not see colleagues' tasks outside shared projects. Leaders also see the tasks of everyone in any of their teams; Managers see everything. Outside their own projects, Leaders and Managers get view + comment only.
- No approval workflow: tasks are just marked done, which notifies the assignee's Leader and all Managers through the in-app bell (no email).
- @mentions in task comments and requirement feedback, stored inline as `@[Name](userId)`. Only people who can see the task (`taskAccess`) or open the project (`projectAccess`) can be mentioned; the server turns any other mention into plain "@Name" and notifies only valid ones (`type = 'mention'`, with an excerpt). Never notify someone about something they cannot open.
- Notifications: `task_completed`, `mention`, `assigned` (when a task is assigned to someone other than the person assigning). They are pushed live over Server-Sent Events (`GET /api/events`, read with fetch so the token stays in a header); every place that creates notifications must call `pushNotifications(userIds)` after its transaction. The client still polls every 30s as a fallback.
- Saved filters and weekly reports (decided 2026-10-09, schema v41): "☆ Lưu bộ lọc" (`components/SavedFilters.jsx`) on a project, My tasks and Work tracking saves the screen's URL hash (filters and view, without `?task=`) as a chip above its filters; each person's own (`saved_filters`, `routes/savedFilters.js`, up to 20 per screen, a project's go with it), shared only by sending the link. At 8:00 on Monday (`lib/reports.js`, once per week) last week (Monday to Sunday) is written to `weekly_reports` as it stands: per team and for the department, tasks done that week (and late), open overdue and due in the next 7 days, each person and who is overloaded (thresholds in `app_state`, default 3 overdue or 8 due soon, set by users.manage 'all' on the Administration card, applying from the next report). Everyone at work with people.watch gets one `weekly_report` notification and reads it at "Báo cáo" (its own sidebar item next to Dashboard since 2026-10-10) › "Bản chốt thứ Hai" (`#/report/<monday>`, `ReportPage.jsx`) within their scope (`reportFor()`: their teams, the department with 'all'). Past reports never change. Reports at any time (decided 2026-10-10): the same page works a report out when opened for a week, a month or any range up to 366 days (`GET /api/reports/range?from=&to=`, `liveReport()`; `#/report/week/<monday>`, `#/report/month/<yyyy-mm>`, `#/report/range/<from>/<to>`, `#/report` = this week): tasks done in the range, and open / overdue / due in 7 days as of its last day (today while it runs; a task counts as open then if created by that day and not done by it), against the range before (`previousRange()`: the month before a whole month, else as many days just before). People, teams and assignees are today's. Pie charts on top (decided 2026-10-10, `ReportCharts.jsx`, `breakdown` from `breakdownFor()`, also on kept weekly reports for their week): the top-level tasks worked on in the range (created by its last day, not done before its first), by activity or project (a switch), by priority and by status as of the last day, within the same scope as the rest of the report; six slices at most, the rest in "Khác"; colors `--cat-1…6` / `--prio-*` in tokens.css.
- Start dates and the Timeline (decided 2026-10-08, schema v40): top-level tasks carry `start_date` (task panel, a List column), never after `due_date` (`PATCH /api/tasks/:id` checks the final pair, 400; subtasks have none). The project's "Timeline" tab (`TimelineView.jsx`, `#/project/3/timeline`, shares the Board / List / Calendar filters) draws a bar from start to due (one date = a one-day bar), grouped by requirement (default), status or assignee (`?group=status|assignee`), at a Day / Week / Month scale; overdue bars are crimson and their names carry ⚠, done ones gray. Whoever may edit a task drags the bar (both dates), an end (one date) or, on a task without dates, along its row (draws them); touch screens hold 0.35 s first. Dragging on a Calendar moves the start date along (`movedTo()` in `utils.js`). Recurring occurrences keep the lead time; templates carry the start date (`start_offset`). Start date changes go to the task history but not to followers. Task dependencies were left for later.
- Project templates (decided 2026-10-08, schema v39): "Lưu làm mẫu" (⧉ in the project header, `POST /api/projects/:id/template`, new or over an existing one) stores a snapshot (`project_templates.data`, `snapshotProject()` in `lib/templates.js`) of the added statuses, requirements, top-level tasks and subtasks (description, priority, channels, assignee, repeat rule) with due dates as day offsets from the earliest; no comments, files, history, members or done ticks (a done task comes back in Planned). Later changes to the project never reach the template. "Tạo project" offers "Bắt đầu từ" (empty or a template, renamed / deleted right there); a template with due dates needs a day picked as the start (earliest due date) or the launch (latest, counting back) (`fillFromTemplate()`). Assignees are kept only while `canBeAssigned()` in the new project (active, not root; they join it and get `assigned`), else left empty. Templates are shared by everyone holding `projects.create`, who list, save (from a project they can open), rename and delete them; no other permission. A new field of tasks or requirements that a template should carry goes into both functions.
- Following tasks and due date reminders (decided 2026-10-08, schema v38): a task's assignee, creator and commenters follow it on their own (`follow()` in `lib/notifications.js`, `task_followers`); anyone who can see it follows or stops by hand ("🔔 Theo dõi" in the task panel, `POST /api/tasks/:id/follow`), and stopping stays (`following = 0`, never re-added). Followers are told of comments (`comment`), due date (`task_due`), assignee (`task_assignee`) and status changes (`task_status`; a subtask's tick: `task_done` / `task_reopened`), never the actor and never twice: someone already told the same thing (mentioned, newly assigned, told it was completed) is skipped (`notifyTaskChanges()` / `notifyFollowers()` with `skip`). Only people at work who can still see the task, never root (`followersOf()`). Any new way of changing a task's due date, assignee or status must call `notifyTaskChanges()`; a recurring task's next occurrence keeps the followers. At 8:00 Monday to Friday (`TZ`, default Asia/Ho_Chi_Minh in `config.js`) everyone at work with open top-level tasks overdue, due today or due by the next work day (Friday: through Monday) gets one `due_digest` notification (counts as JSON in `excerpt`, no task, opens My tasks); once a day (`app_state`), sent late if the server was down at 8:00 (`lib/reminders.js`).
- Invitations (decided 2026-10-06, schema v25): inviting creates the account at once (nothing is emailed), but it counts as joined only from its first sign-in (`users.joined_at`; `joined` in `USER_SELECT`), which is how the person accepts. Until then it shows "Đã mời, chưa tham gia", is not assigned (`canBeAssigned()`, `assignableBy()`), added to projects, listed in `/people` or counted in the workload, and its invitation can be revoked (`DELETE /api/admin/users/:id` deletes the unused account) by the inviter, or by users.manage / root for roles not above their own. Any new place that picks people to work with must leave out accounts that have not joined. Root invites too ("Mời người dùng mới" on System configuration, `POST /api/admin/users` with a role up to the inviter's level).
- Login is Google only, with self sign-up. New accounts stay pending until a Manager approves them; a Leader may also approve self sign-ups straight into one of their teams. Leaders manage their own teams' members (add teamless Members, invite emails, remove Members); a Leader's invitation stays pending until a Manager approves it (`users.invited_by`, v10). Managers' invitations are active at once. `MANAGER_EMAILS` bootstraps the first Manager; `DEV_LOGIN=1` is for local development only.

- Projects belong to one or more teams (`project_teams`; no rows = "Chung toàn phòng"; the old `projects.team_id` column is unused legacy). The sidebar ("Projects theo team", the same for every role, decided 2026-10-06) has one "Team <name>" group per team of the user, even when empty, with every project of that team (a project shared by several own teams shows under each, so each group's count is that team's project count: the user wants to see it at a glance); projects outside the user's teams go to "Project khác", department-wide ones to "Chung toàn phòng" (`groupByTeam()` in `Sidebar.jsx`). Members can still come from any team.
  - Only Managers create projects (decided 2026-10-05) and choose or change their teams; optionally the whole team(s) become members.
  - Project access is `projectAccess()` in `server/src/lib/access.js`: `manage` = owner or the Leader of any of the project's teams (rename, delete, members); `edit` = members; `view` = Managers on every project (read + comment).
  - Project roles (decided 2026-10-07, schema v30): whoever manages a project gives a member a role by hand (`project_members.role`, `PATCH /api/projects/:id/members/:userId`): `admin` (manage + task admin + requirements, but not deleting the project), `member` (edit, own tasks, assignable even from another team) or `viewer` (view + comment, never assigned). A set role wins over the team rules in both directions (it can restrict a Leader); NULL = the team rules decide. No role applies to the owner or to whoever manages every project (`roleFixed()`: projects.manage 'all', the Director by default), nor is it set on oneself or on a higher role level. `projectAccess()`, `isTaskAdmin()`, `canBeAssigned()`, `assignableBy()` and `canEditRequirements()` (now in `lib/access.js`) all read it; any new project right must too. The client reads `project.role` / `task_admin` / `can_edit_requirements` from the server instead of re-deriving them; the members list carries `role`, `team_role` (what the team rules give), `fixed`, `can_set_role`.
  - Task rights (decided 2026-10-05): full rights (create, edit, assign, delete tasks; add / rename / delete sections) only for task admins, `isTaskAdmin()`: Managers and Leaders who belong to a team of the project (department-wide project: any Manager, and Leaders who can open it). Everyone else with `edit` access, owners included, creates tasks that are assigned to themselves and edits only tasks assigned to them (no reassigning, no deleting, subtasks included); other tasks are view + comment. `taskAccess()` returns `admin` / `edit` / `view`.
  - Task admins assign to themselves and to active people of their own teams that take part in the project (`assignableBy()`; department-wide: any own team); assigning a non-member adds them to the project.
  - Only people of the project's teams are given its tasks (department-wide project: anyone in a team), decided 2026-10-06: `canBeAssigned()`. Project members from other teams view and comment but are neither assigned nor add tasks for themselves (`project.can_add_tasks`); tasks assigned before keep their assignee.
  - Model: Project → Requirements → Tasks → Subtasks. Every top-level task belongs to exactly one requirement of its project (`tasks.requirement_id`, required, can move to another requirement but never be cleared); subtasks follow their parent and have no requirement. New projects start without requirements, so the first requirement must exist before tasks can be added.
  - Requirements (title, description, progress = done/total top-level tasks) are created, edited and deleted by the owner, a Leader of one of the project's teams, or any Manager (`canEditRequirements()`). A requirement that still has tasks cannot be deleted. Feedback is per requirement (`requirement_comments`); anyone who can open the project may comment.

- Feedback (decided 2026-10-08, schema v31): any company user sends feedback on the app ("Feedback" at the foot of the sidebar, under "Hướng dẫn"; `#/feedback`, `features/feedback/`): type `bug` / `idea` / `other`, title, text, files (screenshots); the screen they came from, the app version and the browser are recorded. Only the sender and root see it (`loadFeedback()` in `lib/feedback.js`, 404 for anyone else, Managers included). Statuses `sent` → `received` → `in_progress` → `done`, or `rejected` (needs a reason, posted in the thread); root moves them freely (skipping or going back), on the Feedback tab of the System configuration screen. The sender edits, deletes and changes the files of their feedback only while it is `sent` (`editable()`); root deletes any. Each feedback has a thread between the sender and root (`feedback_messages`, with files; the author edits, the author or root deletes) and a status history (`feedback_events`). Notifications: root on a new feedback and on the sender's messages, the sender on a status change and on root's messages (`feedback_new` / `feedback_status` / `feedback_message`). They never go in the bell (decided 2026-10-08, the user found them burying the work ones): `GET /api/notifications` lists the work only and returns `unreadFeedback`, shown as a badge on the Feedback menu (on root's Feedback tab; root has no bell); each feedback in the lists carries `unread` and is labelled "Mới"; opening it (`GET /api/feedback/:id`) reads them; the bell's "read all" leaves them. Live updates go only to the sender and root (`event: feedback`, `pushFeedbackChange()`).
- Chat (decided 2026-10-08, schema v32): "Tin nhắn" (EN "Messages", `#/chat`, `#/chat/4`, `features/chat/`, under "Task của tôi" in the sidebar) holds one-to-one conversations (`conversations` with `kind = 'direct'` and `direct_key` "<smaller id>:<larger id>", `conversation_members.last_read_id`, `messages`). Anyone at work (`AT_WORK`) holding `chat.use` (default: every role) messages anyone else who also does (`canChatWith()` in `lib/chat.js`); someone locked, not yet joined or without `chat.use` gets no new message (400), the old ones stay readable. Private: only the two members read a conversation, nobody else, Managers, Directors and root included (`loadConversation()`, 404; root gets 403 as usual). Only the author edits or deletes a message; deleting keeps the row (`deleted_at`, text emptied, files removed) shown as "Tin nhắn đã bị xoá". Files go with a message (`attachments.message_id`), sent by its author, seen by both members, deleted by the uploader. Unread messages never go in the bell: `unreadChat` from `GET /api/notifications` is the badge on the menu; opening a conversation in a visible tab reads it ("Đã xem" for the other side). Live updates go only to the two members (`event: chat`, `pushChat()`). Messages older than 6 months are deleted at startup and daily (`purgeMessages()`, then `sweepUploads()`). Groups, project and team chats (decided 2026-10-08, schema v33): `kind = 'group'` (title; `owner_id` renames and takes people out; anyone in it adds people who can be messaged or leaves; when the owner leaves the member who joined first, by `conversation_members` rowid, takes over; the last one out deletes it), `'project'` (`project_id`: whoever can open the project, `projectAccess()`, like its comments; the "Chat" button in the project header) and `'team'` (`team_id`: the people of the team). Project and team members come from those rules at each request (`memberUsers()` / `isMember()` in `lib/chat.js`), so losing the access ends the reading at once; their `conversation_members` rows only keep `last_read_id` and `muted`. @mentions are kept for members only (`resolveMentions()` with `reachableMembers()`) and never go to the bell: the conversation shows "@" and a muted one still counts the messages that mention the user (`totalUnread()`). "Trả lời" sets `messages.reply_to_id` (same conversation only). A link to a task (`#/task/<id>`, or any screen with its panel open, `?task=<id>`) shows the task's name only to readers who can see it (`taskLinks()`, `taskAccess()`), as a chip that opens it. System lines (decided 2026-10-08, schema v34): every change to a group (created, people added or taken out, someone leaving, the owner handing on, a new name) is written into it as a message with `kind = 'system'` by its actor (`systemLine()` in `routes/chat.js`; `data` keeps the names as they were); its body holds the @[Name](id) of the people it is about, and only for them it counts as unread (`unreadOf()`), never as a mention. People added to a group start with the messages from before as read, so they get exactly one unread line. System lines are never edited, deleted or answered; any new change to a group's members or name must write one. Reactions, read-by, alerts (decided 2026-10-08, schema v35): one reaction per person per message from a fixed set (`REACTIONS` in `lib/chat.js` and `ChatParts.jsx`, `message_reactions`); deleting a message drops them. Reading is pushed to every member, and in a group, project or team each member's avatar shows under the last message they read. Someone who comes into a project or team chat after its last message has no row there and nothing unread (`unreadFor()`); `markNewcomers()` gives everyone in it a row at the current last message before each new one, so only messages from then on are unread for them. Alerts stay out of the bell: the tab title counts bell + messages, a sound plays for a new message outside the conversation on screen, a desktop notification while the tab is hidden (`client/src/chatAlerts.js`, permission asked from the Messages screen). Pins, forwarding, @tất cả, search (decided 2026-10-08, schema v36): anyone in a conversation pins or unpins a message (a system line says so, `messages.pinned_at`); forwarding copies the text and files to another conversation the user can write in, marked only "Đã chuyển tiếp", never naming the author or the source; @tất cả (`@[all](0)`, `EVERYONE_ID` 0) mentions everyone in a group, project or team chat, anyone may use it, and in a one-to-one chat it becomes plain text; search is accent-insensitive over `messages.search` (`foldText()` in `lib/fold.js`, kept in step on every send / edit / delete), only in the user's own conversations. Polls, timed mute, pinned conversations (decided 2026-10-08, schema v37): a poll rides on a message (its body is the question; tables `polls`, `poll_options`, `poll_votes`, rules in `lib/polls.js`), only in group, project and team chats, created by anyone in them; its creator chooses several choices or one, others adding options, an optional deadline, and may close it; votes are public (names shown), changeable while open, never count as unread; a poll is neither edited nor forwarded. Muting takes `hours` 1 or 8 (`muted_until`) or lasts until turned back on. Each person pins up to 5 conversations to the top of their own list (`conversation_members.pinned_at`, `pinned_chat` in the summary; `pinned` there is the list of pinned messages). `transaction()` joins an open transaction instead of nesting.
