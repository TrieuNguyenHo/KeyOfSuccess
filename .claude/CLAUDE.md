# KeyOfSuccess (formerly TaskFlow)

Asana-like task manager for a Marketing department of about 40 people.
React + Vite (`client/`), Node/Express + SQLite via `node:sqlite` (`server/`). Run with `npm run dev` from the repo root.
README.md documents setup, env vars, permissions and the API.

Server layout (split 2026-10-06): `server/src/index.js` only builds the app; each feature's endpoints are an `express.Router` in `server/src/routes/<feature>.js` (mounted under `/api`), and rules or helpers used by more than one route live in `server/src/lib/` (access rules in `lib/access.js`). A new endpoint goes in its feature's route file, never back into `index.js`.

Client layout (split 2026-10-06): screens live in `client/src/features/<feature>/`, components shared by several screens in `client/src/components/` (one file per concern: `Avatar`, `TaskParts`, `Mentions`, `Controls`, `Preferences`, `hooks`, `Dialog`, `CurrentUser`), styles in `client/src/styles/` imported in order by `styles/index.css` (tokens first, `responsive.css` last; new rules go in the matching file, before `responsive.css`). Import straight from the file that defines a thing; there is no barrel file.

Production (2026-10-06): `npm run build` then `npm start` with `NODE_ENV=production` in `server/.env`; one process serves the API and `client/dist`, HTTPS comes from a reverse proxy (`deploy/Caddyfile`, `deploy/keyofsuccess.service`). `config.js` refuses to start without a real `JWT_SECRET` / `GOOGLE_CLIENT_ID` or with `DEV_LOGIN`. Daily backups of the database and uploads (`lib/backup.js`, `BACKUP_DIR`, `npm run backup`); any new folder of user data under `server/data/` must be added to them. Versions are git tags on `main`; `deploy/update.sh [tag]` deploys one (backup first, automatic rollback if the app does not come up), `deploy/rollback.sh [--list | tag]` goes back (code only when the schema matches, else restores the pre-deploy backup); history in `server/data/deploys.log`. Migrations only run forward, so a schema change makes rolling back cost the data entered since. `DEPLOY.md` is the step-by-step guide (keep it in step with the scripts); README › Deploy has the technical details.

Tests: `npm test` (node:test, `server/test/*.test.js`, about 5 seconds). Each file starts its own API on a free port with a temporary database, so it is safe while the dev server runs. Run it after every server change; a new rule or endpoint gets tests in the matching file (helpers in `server/test/helpers.js`). Do not write ad-hoc curl scripts for API checks.

Schema changes: `npm run dev` runs the server with `node --watch`, so saving `server/src/db.js` immediately runs new migrations on the real `server/data/app.db`. Before editing the schema, stop the dev server and back up the database (`VACUUM INTO 'data/app.backup-<name>.db'`), then test migrations on a copy.

## Languages (decided 2026-10-06, schema v19)

The interface is in Vietnamese or English, per account (`users.language`, `PATCH /api/me`, VI | EN switch in the sidebar and on the sign-in / waiting screens; default Vietnamese). Every user-facing text in the client goes through `tr('Vietnamese text', { params })` from `client/src/i18n.js`, with its English in `client/src/i18n.en.js` (the Vietnamese is the key; `{name}` placeholders). Never translate user content (project, task, status, requirement names). Label tables and other module-level text must be getters or functions so they read the current language. The server keeps answering in Vietnamese; `trMessage()` translates its errors, so a new server message needs an English entry too. `server/test/i18n.test.js` fails on a missing English text or a Vietnamese text outside `tr()`. Dates use `locale()`.

## UI design

App name (decided 2026-10-06): "KeyOfSuccess", K and S being KingSport's initials. On screen it is always `<Brand />` (`client/src/components/Brand.jsx`): O 2× the other letters and K and S twice the O (4×), K and S in `--brand` (large text only) (updated by the user the same day; earlier tries: 8× with "Keyof", then 5×); `--brand-size` sets the small letters (12px sidebar and top bar, 18px sign-in card, 14px there on phones). Internal ids keep the old name (`taskflow_theme` in localStorage, the `taskflow-theme` event): renaming them would reset saved choices.

Before any UI work (components, CSS, layout, colors, typography), read `.claude/DESIGN.md` and follow its tokens and do/don't rules.

Exception, chosen by the user: colors follow the KingSport brand (red-white), not DESIGN.md's Action Blue. The tokens live in `client/src/styles/tokens.css`:
- `--brand` #D85A30 (only 3.87:1 on white): large fills, chart marks, login background. Never small text.
- `--primary` #C24E26: buttons and other filled controls with white text (4.76:1).
- `--primary-text` #993C1D: links and red text on white.
- Overdue/destructive is crimson `--danger` #B42318 and always pairs with a ⚠ icon, because it sits close to the brand red.
- Light and dark themes: `:root` holds light tokens, `:root[data-theme='dark']` overrides them (index.html sets `data-theme` before first paint from localStorage `taskflow_theme`, else the OS preference). Never hard-code a color outside those token blocks, except the sidebar's own `--sb-*` tokens (dark #1E2027 panel from `component_styles/side_bar`, same in both themes, brand red only as accent). Re-check contrast (and chart pairs with the dataviz validator) for both themes when adding colors.

## Product rules (decided with the user, 2026-10-05)

- Root (decided 2026-10-06, schema v23): accounts in `ROOT_EMAILS` (`users.role = 'root'`) are not part of the company. They only configure the system on the "Cấu hình hệ thống" screen (`SystemConfigPage.jsx`, shown instead of the Workspace): roles (the Director role included), status and teams of people. `ROOT_ROUTES` in `routes/auth.js` lets them reach only `/me`, `/admin/users`, `GET /teams` and avatars; everything else is 403, and they read nobody's personal details. Root has no teams and is left out of every list of people (`u.role != 'root'` in the user list, team candidates, `/people`, the dashboard workload, adding project members); nobody changes a root account in the app (404), and an email taken out of `ROOT_EMAILS` loses access at the next request. Root is not a role anyone can give. Root also edits the permissions (below).
- Permissions (decided 2026-10-06, schema v24): what each role may do is data, set by root ("Quyền theo vai trò" on the System configuration screen): `roles` (key, name, `level`) and `role_permissions` (role, permission, scope `none` / `team` / `all`). The catalog and the defaults live in `server/src/lib/permissions.js`; the defaults are the rules described in this file, which therefore describe default behaviour. Never check `user.role` for a right: use `can()` / `scopeOf()` / `coversTeams()` (server `lib/permissions.js`, client `utils.js` reading `user.permissions` from `/api/me`) or the `requirePermission(key)` guard; a new right gets a new permission with its defaults (seeded at startup). Role levels replace the hard-coded Director rule: nobody changes the account of, gives, or reads the profile of a role above their own (`outranks()`, root above all). Roles are editable (decided 2026-10-07, schema v27): root adds a role as a copy of another (permissions and team rule) at a level it picks, renames any role, deletes an added role nobody holds (pending and locked accounts count); the four built-in roles (`roles.builtin`) keep their level and are never deleted, since sign-up and Leader invitations give `member` and `MANAGER_EMAILS` / `DIRECTOR_EMAILS` give `manager` / `director`. Each role carries its team rule, `min_teams` 0 / 1 and `max_teams` 1 / NULL (no limit): never test `role === 'member'` or `'leader'` for team counts, use `teamLimitsError()` / `singleTeam()` (server) or `roleIn(roles, key)` (client); a rule cannot change while a holder breaks it. Without users.manage, team member management reaches people of a lower level only. `users.role` has no CHECK since v27. Role names come from the server (`role_name` in `USER_SELECT`, `roleLabel(user)` in the client), never from a hard-coded list.
- Managers run their own teams only (decided 2026-10-06, schema v26): every team-scoped Manager permission defaults to 'team' (projects.view, projects.change_teams, requirements.manage, people.watch, people.profiles, users.manage, teams.members, teams.manage, notify.task_completed); only the Director sees the whole department. users.manage 'team' covers the people of one's teams and those with no team (never a higher role) and places them only in one's teams (`mergeOwnTeams()` keeps their other teams); teams.manage 'team' renames one's teams, creating / deleting needs 'all'; projects.change_teams 'team' picks among one's teams, at least one. The rules below that say "Managers see everything" / "every project" describe a Manager given 'all' by root. Test files written before v26 run with the Manager at 'all' (`startServer()` in `server/test/helpers.js`); `startServer({ managerScope: 'team' })` tests the default.
- Director (decided 2026-10-06, schema v22): above the Managers, full rights on the whole system. Has every Manager right (`isManager()` in `server/src/lib/roles.js` and `client/src/utils.js` is true for both; use it, not `role === 'manager'`, for Manager-level rights), plus `manage` access and task admin on every project, assigning anyone of the project's teams. Only a Director or root gives / removes the Director role or changes a Director's account (role, status, teams); a Director's profile is for Directors only. Directors get no `task_completed` notifications. `DIRECTOR_EMAILS` bootstraps them (Trieu is Director); `MANAGER_EMAILS` never demotes a Director. The lists give their role once (decided 2026-10-07, schema v29: `users.env_role` = the role the lists last gave; sign-in applies it only when the lists say something new), so a role change or a lock made in the app survives the next sign-in; `envRoleOf()` in `config.js`. A Director belongs to any number of teams, like a Manager.
- Roles: Manager runs the whole department and is also admin; Leader runs one or more teams. Teams live in `user_teams` (v9; `users.team_id` is unused legacy): a Member belongs to exactly one team, a Leader to at least one and leads all of them, a Manager to any number. Users carry `teams`, `team_ids` and `team_name` (names joined).
- Visibility: Members see only projects they belong to and must not see colleagues' tasks outside shared projects. Leaders also see the tasks of everyone in any of their teams; Managers see everything. Outside their own projects, Leaders and Managers get view + comment only.
- No approval workflow: tasks are just marked done, which notifies the assignee's Leader and all Managers through the in-app bell (no email).
- @mentions in task comments and requirement feedback, stored inline as `@[Name](userId)`. Only people who can see the task (`taskAccess`) or open the project (`projectAccess`) can be mentioned; the server turns any other mention into plain "@Name" and notifies only valid ones (`type = 'mention'`, with an excerpt). Never notify someone about something they cannot open.
- Notifications: `task_completed`, `mention`, `assigned` (when a task is assigned to someone other than the person assigning). They are pushed live over Server-Sent Events (`GET /api/events`, read with fetch so the token stays in a header); every place that creates notifications must call `pushNotifications(userIds)` after its transaction. The client still polls every 30s as a fallback.
- Invitations (decided 2026-10-06, schema v25): inviting creates the account at once (nothing is emailed), but it counts as joined only from its first sign-in (`users.joined_at`; `joined` in `USER_SELECT`), which is how the person accepts. Until then it shows "Đã mời, chưa tham gia", is not assigned (`canBeAssigned()`, `assignableBy()`), added to projects, listed in `/people` or counted in the workload, and its invitation can be revoked (`DELETE /api/admin/users/:id` deletes the unused account) by the inviter, or by users.manage / root for roles not above their own. Any new place that picks people to work with must leave out accounts that have not joined. Root invites too ("Mời người dùng mới" on System configuration, `POST /api/admin/users` with a role up to the inviter's level).
- Login is Google only, with self sign-up. New accounts stay pending until a Manager approves them; a Leader may also approve self sign-ups straight into one of their teams. Leaders manage their own teams' members (add teamless Members, invite emails, remove Members); a Leader's invitation stays pending until a Manager approves it (`users.invited_by`, v10). Managers' invitations are active at once. `MANAGER_EMAILS` bootstraps the first Manager; `DEV_LOGIN=1` is for local development only.

- Projects belong to one or more teams (`project_teams`; no rows = "Chung toàn phòng"; the old `projects.team_id` column is unused legacy). The sidebar ("Projects theo team", the same for every role, decided 2026-10-06) has one "Team <name>" group per team of the user, even when empty, with every project of that team (a project shared by several own teams shows under each, so each group's count is that team's project count: the user wants to see it at a glance); projects outside the user's teams go to "Project khác", department-wide ones to "Chung toàn phòng" (`groupByTeam()` in `Sidebar.jsx`). Members can still come from any team.
  - Only Managers create projects (decided 2026-10-05) and choose or change their teams; optionally the whole team(s) become members.
  - Project access is `projectAccess()` in `server/src/lib/access.js`: `manage` = owner or the Leader of any of the project's teams (rename, delete, members); `edit` = members; `view` = Managers on every project (read + comment).
  - Task rights (decided 2026-10-05): full rights (create, edit, assign, delete tasks; add / rename / delete sections) only for task admins, `isTaskAdmin()`: Managers and Leaders who belong to a team of the project (department-wide project: any Manager, and Leaders who can open it). Everyone else with `edit` access, owners included, creates tasks that are assigned to themselves and edits only tasks assigned to them (no reassigning, no deleting, subtasks included); other tasks are view + comment. `taskAccess()` returns `admin` / `edit` / `view`.
  - Task admins assign to themselves and to active people of their own teams that take part in the project (`assignableBy()`; department-wide: any own team); assigning a non-member adds them to the project.
  - Only people of the project's teams are given its tasks (department-wide project: anyone in a team), decided 2026-10-06: `canBeAssigned()`. Project members from other teams view and comment but are neither assigned nor add tasks for themselves (`project.can_add_tasks`); tasks assigned before keep their assignee.
  - Model: Project → Requirements → Tasks → Subtasks. Every top-level task belongs to exactly one requirement of its project (`tasks.requirement_id`, required, can move to another requirement but never be cleared); subtasks follow their parent and have no requirement. New projects start without requirements, so the first requirement must exist before tasks can be added.
  - Requirements (title, description, progress = done/total top-level tasks) are created, edited and deleted by the owner, a Leader of one of the project's teams, or any Manager (`canEditRequirements()`). A requirement that still has tasks cannot be deleted. Feedback is per requirement (`requirement_comments`); anyone who can open the project may comment.

- Profile (decided 2026-10-06, schema v20): `#/profile` (the user's own name at the foot of the sidebar) shows the account (read only) and lets the user edit their display name, birthday, gender, phone, job title and bio through `PATCH /api/me`, plus Light / Dark and VI / EN (the sidebar keeps its switches too). Personal details are private: only the user, Managers and the Leaders of any team the user belongs to read them, except that a Manager's profile is for Managers only (decided 2026-10-06: `canReadProfile()` / `GET /api/users/:id/profile`, 404 for anyone else; `withProfile()` in `server/src/lib/users.js` is used only there, by `/api/me` and by the `/api/admin/users` routes). They open read only by clicking a person's avatar in User management › Users and in team member lists (`ProfilePopover` in `ProfilePage.jsx`). Never add them to `USER_SELECT`, which feeds what others see about a person. The profile picture (v21, `users.avatar`) is not private: everyone signed in sees it wherever `<Avatar userId=…>` is drawn (always pass `userId`); it is cropped to 256 px in the browser, checked by its bytes on the server (PNG / JPG / WebP, ≤ 1 MB), fetched with the token and cached per version (`client/src/avatars.js`). `sweepUploads()` must keep avatar files.
- Comments and requirement feedback (decided 2026-10-05): only the author edits (`edited_at`, "đã sửa"; people newly mentioned by the edit are notified); the author or any Manager deletes. Nobody edits someone else's words.
- Attachments (decided 2026-10-05, schema v11): on tasks and requirements, 25 MB per file. Whoever can comment can attach; the uploader, task admins (task files) or requirement editors (requirement files) delete. Bytes live in `server/data/uploads/` (back it up with the database); only PNG/JPEG/GIF/WebP are served as themselves, everything else as a download.
- Files in comments (decided 2026-10-06, schema v13): task comments and requirement feedback can carry files (`attachments.comment_id` / `requirement_comment_id`; the row keeps its task / requirement for access). Only the comment's author attaches; a comment may be files only (`with_files: true`); deleting a comment deletes its files. The task's / requirement's own "Đính kèm" list leaves comment files out.
- Task team tags (decided 2026-10-06, schema v16 dropped the v14 requirement labels): a task shows its assignee's teams that take part in the project (all their teams for a department-wide project, or for an old assignee outside the project's teams), as `assignee_teams` from `GET /api/projects/:id`. The project's "Mọi team" filter uses them.
- Channels (decided 2026-10-06, schema v17): one department-wide list (`channels`: name, color) that only Managers add / rename / recolor / delete (Quản lý người dùng). Top-level tasks carry any number of them (`task_channels`), set by whoever may edit the task (`PATCH /api/tasks/:id` with `channel_ids`); subtasks carry none. Tags show on Board / List / Task của tôi / Theo dõi (calendar: in the tooltip); the "Mọi kênh" filter (project, Task của tôi, Theo dõi) is `?channel=<id>`. Both dashboards have "Theo kênh" (`channelBreakdown()`: a task counts in each of its channels, plus "Chưa gắn kênh"), within the dashboard's usual scope. Changes, including a deleted channel leaving its tasks, go to the task history. Only Managers see per-channel task counts.
- Recurring tasks (decided 2026-10-06, schema v18): a top-level task may carry a repeat rule (`tasks.recurrence`: daily Mon–Fri, weekly / biweekly on chosen weekdays, monthly on day 1–31 = last day of shorter months), set by whoever may edit it. Completing it (any way: `PATCH` completed or a move into the done status) runs `spawnNextOccurrence()` in `server/src/lib/recurrence.js`: a copy (title, description, assignee if `canBeAssigned()`, requirement, priority, channels, unticked subtasks) in the to-do status, due on the rule's next day after the old due date and never before today; the rule moves to it and `next_task_id` makes each occurrence spawn once. Completing a daily task does not send `task_completed`; the new occurrence sends `assigned` when someone else ticked it.
- Task history (decided 2026-10-06, schema v15): `task_events` records every change to a task for 30 days (purged at startup and daily): creation, each field change (old → new, stored as readable names; descriptions keep both texts), comments added / edited / deleted, files added / deleted, subtasks added / changed / deleted (kept on the parent). Anyone who can see the task reads it (`GET /api/tasks/:id/history`). Any new way of changing a task must call `logEvent()` / `logTaskChanges()` in `server/src/lib/history.js`.
- Calendar (decided 2026-10-05): a "Lịch" tab in projects (shares the Board/List filters) and a Danh sách / Lịch switch on Task của tôi and Theo dõi; dragging a task to another day sets its due date when the user may edit it.
- Wording (decided 2026-10-06): task comments and requirement feedback (`requirement_comments`) read the same, never "Góp ý": heading "Comments", composer placeholder "Gõ @ để nhắc ai đó, dán ảnh hoặc bấm 📎 để đính kèm", empty "Chưa có comments.", delete dialog "Xoá comment này?", API error "Comment không được để trống". The UI says "comment(s)" everywhere, never "bình luận" (history lines, read-only notes, delete dialogs).
- Wording (decided 2026-10-06): sections (board columns) are called "trạng thái" everywhere in the UI and in API error messages; the code keeps `sections` / `section_id`. The project's status filter lists only them (`status=s<id>` in the URL); there is no separate done / not-done filter.
- Statuses and the done tick (decided 2026-10-06, schema v12; four fixed statuses since v28, which was v26 on the deployed v1.0 line: see the merge note in `server/src/db.js`): every project has Planned / In-Progress / Completed / Pending (`sections.kind` todo / doing / done / pending). Their names are fixed and identical in Vietnamese and English (stored as is, never passed through `tr()`), and they can be neither renamed nor deleted (no ✎ / ✕, server 400); added statuses can be both. In a project with a done status, `statusSync()` in `server/src/lib/statuses.js` keeps top-level tasks in step: ticking moves the task to the end of Completed, unticking moves it to In-Progress (else the first other status); moving it into Completed ticks it (and notifies, like ticking), moving it out unticks it; a task created in Completed is done. Pending is an ordinary open status. Subtasks only have the tick.
- Dashboards (decided 2026-10-05): the overview (`/api/dashboard`) is for Leaders (their teams) and Managers; Members get a Dashboard menu with only the project dashboards of their projects.

New features must respect these rules, e.g. a dashboard shows a Leader only their own team.
